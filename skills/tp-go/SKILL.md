# Deliver the requested change

Follow [the shared flow](references/shared-flow.md) through Product → Design →
Plan → Build → Evaluate → Engineering → Retro. Preserve accepted decisions and
the user's scope. Manual approval is the default: each concrete phase result
requires separate human approval. Optional automatic mode requires explicit
run-bound policy authorization, scoped conditions and named stop phases; one
phase approval never enrolls a policy or combines checkpoints.

Start with the goal, stable acceptance criteria, material boundaries and current
output. Design chooses the approach; Plan specifies exact Build paths, owners,
prerequisites and meaningful checks. Do not demand all future filenames before
Product. Implement only after Plan acceptance. Remove obsolete tests, fixtures,
imports and CI references with removed code.

Initialize in the actual native task workspace before presenting Product. New
repository runs require a clean dedicated linked worktree and intended base.
Report matching automatic pre/post observations as coverage, not root phase
authority. Missing callbacks do not require a restart or veto valid root work;
native worker readiness remains separate. Preserve existing work and decisions. Initial and relevant
milestone scans use the existing decomposed graph cache; report failed or stale
views explicitly. Task completion is separate from phase approval.

Use a durable brief and follow relevant source/evidence references. No receipt,
byte accounting, startup probe or full conversation replay is required. Delegate
useful disjoint work when authorized; this skill authorizes such bounded native
work. [Native ownership](references/codex-native-dispatch.md) describes identity,
completion and cancellation requirements without a fan-out default.

Submit the useful result once, present it in the conversation, and wait for its
actual approval. Ordinary contextual assent is enough; ambiguous intent needs
clarification. Publish and show the dashboard at flow start and phase checkpoints;
its rendering is not approval authority. Hooks check the active phase, approvals
and owned task paths before supported actions. Required typed DoR/DoD evidence
must pass before acceptance; equivalent substantive wording is valid.
Retry only missing, failed or invalidated tasks and their affected checks; retain
all unaffected results, evidence and approvals, without restarting earlier phases.
Candidate hook source is editable within its task. Never disable, uninstall or
bypass the live harness to get past a refusal. Preserve the journal improvement.
Report actual checks and limitations, preserve failed/unknown attempts,
and finish only after Retro approval.
