Use the host's supported plugin controls and permitted marketplace. Select the
intended project, review hook definitions/permissions and establish the actual
loaded installation. Python 3.10+ is needed by the runtime; actual host/plugin
support is observed, not inferred from a package label.

```sh
python3 /actual/plugin/taskplane/tp.py version --verify
python3 /actual/plugin/taskplane/tp.py --help
```

Both candidate manifests use `2.34.4`. Keep loaded skills, hooks and runtime on the
same installation. Building archives or editing source does not reload an active
session. Use supported host reload/new-session behavior and preserve the old
runtime/evidence. Do not overwrite an installed cache during an active run.

## First requested work

Retain the user's original repository, route and scope. Help/status/catalog/
validation/preview remain read-only. For execution, inspect the selected folder
and existing run, then perform only required supported initialization/binding.
Missing setup is a concrete blocker; do not ask for another project selection
when already known or redirect a standalone review into full delivery.

New repository work requires a clean dedicated linked worktree at the intended
base. Use the host's workspace selection to execute the actual native chat there;
a worktree attachment or a shell workdir alone does not move it. Declare
`repository`, `base_ref` or `base_revision` in the start scope when needed.
Dirty/shared/foreign destinations are refused without deleting files. After
start, perform an ordinary admitted read so the automatic pre/post pair matches
this run, visit, workspace and loaded runtime before the first phase review.
If readiness is missing, retry this checkpoint after that read; keep prior work.

Start with goal, stable criteria, material boundaries and current output.
Plan later fixes exact Build ownership/paths/checks. Present each concrete phase
for separate approval. Ordinary contextual assent needs no special wording,
dashboard display, receipt or startup ceremony. Use
[shared flow](../skills/tp-go/references/shared-flow.md).

## Cowork workspace and execution

An explicit selected-project binding identifies the permitted project and policy.
Storage visibility, command execution and native worker execution are separate
observations. A connected/mounted Mac folder does not prove local commands or
workers. Preserve strict locality restrictions, supplying actual observation
references through supported binding controls; report a missing capability rather
than substitute a session directory or remote environment.

## Interruptions and recovery

Resume the actual run from its durable brief and relevant evidence. Preserve
accepted decisions, failed attempts, known command handles and uncertain native
cancellation. A Stop or wait/message success cannot prove completion.

Use supported import/binding/relocation controls, preserving authentic original
provenance and complete archived state. Do not fabricate initialization markers
or replace a controller with an old snapshot. Inactive imported stores use their
verified committed import provenance; active/tampered stores refuse relocation.
See [state](state-spec.md) and [state import](state-import-and-release.md).

The candidate reads old-contract history but refuses active mutation. Continue
with the original compatible runtime or explicitly retire and start fresh under
the new contract. Retirement does not approve pending phases. If the user chooses
manual continuation, keep it manual and do not reactivate the retired harness.

## Diagnose one actual failure

Report the failing operation, actual runtime/workspace, reason and next useful
action. Inspect relevant help/state once and retry after a changed condition.
Do not spin on unchanged refusals, weaken permissions or claim unavailable live
acceptance. Unit fixtures, extracted packages, actual platform CI and installed
Codex/Claude journeys are distinct evidence. Initial and milestone graph scans
reuse current source inputs. Dashboard tasks show actual owners, dependencies,
status and available artifacts; phase approval does not complete unfinished work.
Graph/dashboard/usage failures remain explicit derived-view diagnostics and do
not change authority. A requested verification criterion still needs its evidence.
